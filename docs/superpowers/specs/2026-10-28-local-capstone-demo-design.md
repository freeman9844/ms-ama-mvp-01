# Capstone 로컬 데모 설계

## 1. 목적과 승인된 범위

원문의 5개 역할이 어떤 데이터와 상태를 주고받는지 사용자가 로컬 브라우저에서 직접 이해하고 검증할 수 있는 데모를 만든다. 실제 금융 서비스 출시나 신용위험 성능 입증이 목적은 아니다.

근거 문서는 저장소 루트의 `ama-origin.md`, `ama-rubric-01.md`, `ko-origin.md`, `ko-agent-01.md`, `ko-design-01.md`다. 원문의 역할을 다른 5개 역할로 교체하지 않는다.

사용자가 승인한 사항:

- 신청·심사, 정산 지연 경보, 상환 지원, 동의 만료·삭제까지 5개 역할 전체를 포함한다.
- 하나의 저장소에서 모듈형 앱과 별도의 mock HTTP API를 실행한다.
- TypeScript, React, SQLite를 사용하며 업무 DB와 mock 원천 DB를 분리한다.
- Data Assembly와 Consent Lifecycle은 코드로 구현한다.
- Underwriting, Early-Warning, Collections는 GitHub Copilot SDK로 실제 추론한다.
- 사업자 포털을 중심으로 담당자 화면과 데모 제어를 구분한다.
- 고객에게 별도의 수집 결과 승인 단계를 강제하지 않고 필요한 보완만 요청한다.
- 합성 데이터만 사용한다. 실제 대출·송금·고객 메시지 발송은 하지 않는다.
- 앱·데이터는 로컬이지만 Copilot 추론은 원격이며 사용량이 발생한다.

본 문서는 구현 전에 검토할 설계다. 문서 승인 후 별도 구현 계획을 작성하고, 그 계획과 실행 방법을 승인받은 뒤 제품 코드를 작성한다.

## 2. 접근 방식과 기각한 대안

| 접근 방식 | 판단 |
|---|---|
| 모듈형 앱 + 별도 mock API | 채택. 실제 HTTP 수집을 보여주면서 실행·디버깅 부담을 제한한다. |
| 한 저장소에서 5개 HTTP 에이전트 서비스 | 첫 데모에서는 제외. 내부 호출까지 분산하면 프로세스·인증·버전 관리가 늘어난다. |
| 에이전트별 저장소·서비스 | 이후 확장 후보. 이번에는 역할별 인터페이스를 유지하되 저장소는 분리하지 않는다. |
| 별도 LLM Orchestrator | 제외. 업무 순서·권한·상태는 코드가 통제하고 각 역할 안에 필요한 판단을 둔다. |
| Durable Functions·Fabric·메시지 브로커 | 첫 데모에서 제외. 작업 복구를 포함한 소규모 로컬 실행을 구현하며 클라우드 배포는 하지 않는다. |
| 모의 AI 응답만으로 데모 | 제외. 실제 추론이 사용자 요구다. 자동 테스트용 대역과 제품 실행 경로는 분리한다. |

## 3. 논리 구성

```text
React UI
  ├─ 사업자 포털
  ├─ 담당자 화면
  └─ 데모 제어
        ↓ 같은 출처의 업무 API
앱 서버
  ├─ 데모 로그인·권한 검사
  ├─ 코드 오케스트레이터·백그라운드 작업 실행기
  ├─ Consent Lifecycle
  ├─ Data Assembly ── HTTP ── Mock 원천 서버
  ├─ Underwriting ── Copilot SDK
  ├─ Early-Warning ── Copilot SDK
  └─ Collections ── Copilot SDK
        ↓
업무 SQLite                         원천 SQLite
```

Mock 원천 서버는 요청마다 서버 간 인증을 확인하고, 앱의 내부 동의 검사 API를 호출해 현재 원천·사업자·기간·목적의 허용 여부를 확인한다. 고객이 보낸 `consent_verified` 같은 플래그는 사용하지 않는다.

순환 작업 호출은 만들지 않는다. 내부 동의 검사 API는 상태 조회만 수행하며 Data Assembly나 원천 조회를 다시 실행하지 않는다.

## 4. 실행 구성과 파일 책임

제품 코드는 루트의 기존 분석 문서를 유지하며 `demo` 폴더에 둔다.

| 경로 | 책임 |
|---|---|
| `demo\src\web` | React 화면, API 클라이언트, 상태 표시 |
| `demo\src\server` | HTTP 업무 API, 로그인·권한, 앱 수명주기 |
| `demo\src\agents` | 원문의 5개 역할과 구조화된 입출력 |
| `demo\src\workflow` | 작업 큐·상태·재시도·재개·멱등성 |
| `demo\src\domain` | 동의·심사·상환 정책, 정밀 금액·날짜 계산 |
| `demo\src\copilot` | SDK 연결·세션·도구 허용 목록·출력 검증 |
| `demo\src\mock` | 원천 HTTP 서버, 합성 데이터, 사건 생성 |
| `demo\tests` | 단위·통합·브라우저 검증 |
| `demo\.local` | Git 제외 대상 DB·런타임 상태·앱 소유 세션 기록 |

Node.js 24에서 실행한다. React 빌드는 Vite, HTTP 서버는 Express, SQLite 접근은 Node의 `node:sqlite`를 사용한다. TypeScript 빌드·타입 검사와 프로젝트 lint 명령을 준비한다. SDK를 포함한 패키지 버전은 구현 시 호환성을 확인한 뒤 lockfile로 고정한다.

기본 앱 주소는 `http://127.0.0.1:3000`, mock API는 `http://127.0.0.1:3001`이다. 루프백에만 바인딩하고 포트 충돌 시 명시적으로 실패한다. 주소 변경은 실행 설정으로 제공한다.

`demo`에서 하나의 실행 명령으로 UI 빌드와 두 서버를 시작하도록 한다. 개발 시 서버가 준비되었는지 확인하며 종료 시 자신이 시작한 자식 프로세스와 SDK 연결만 정리한다.

## 5. 사용자와 화면

### 5.1 데모 로그인

합성 사업자, 여신 담당자, 데모 운영자라는 고정 테스트 계정을 선택해 로그인한다. 서버가 발급하는 HttpOnly 세션으로 역할·사업자를 결정한다. 업무 요청마다 임의의 역할 헤더나 사업자 ID를 신뢰하지 않는다.

이는 로컬 테스트용 로그인이지 실제 본인확인·운영 인증이 아니다. 로컬 사용자가 다른 데모 계정을 선택할 수 있다는 한계를 화면과 README에 명시한다. 서버 권한 검사는 로그인된 역할의 허용 범위를 강제한다.

상태 변경 요청에는 같은 출처 검사와 세션에 연결된 CSRF 보호를 적용한다. 외부 출처에 API를 개방하지 않는다. 브라우저에 mock 서버 인증정보나 Copilot 인증정보를 보내지 않는다.

### 5.2 사업자 포털

- 홈: 신청 상태, 필요한 보완, 다음 상환 일정.
- 신청: 기본 사업자 정보·희망 조건 → 데이터 동의 → 최종 확인·제출.
- 내 신청: 접수·수집·심사·보완·결과, 실패 시 실행 가능한 안내.
- 데이터 동의: 목적·원천·항목·기간·유효기한, 철회·갱신과 삭제 상태.
- 내 대출·상환: 모의 대출·상환 일정·납부 상태.
- 도움·상환 지원: 고객의 자연어 요청, 접수·검토 상태, 정정·설명·고충 요청.

필수 동의를 사전 선택하지 않는다. 신청 심사용과 사후 모니터링용 동의는 분리한다. 심사 동의가 없으면 신청을 제출할 수 없는 이유를 표시한다. 사후 모니터링 미동의 자체는 이 데모의 자동 거절 사유가 아니며, 모니터링을 실행하지 않는다는 영향을 안내한다.

보완자료는 초기 범위에서 준비된 합성 자료 선택·제출로 제한한다. 실제 금융 문서 업로드는 제공하지 않는다.

### 5.3 담당자 화면

신청 목록과 상세 화면에서 계산 결과, AI 의견, 불확실성, 근거 참조, 도구 활동을 확인한다. 담당자는 승인·거절·보완 요청을 수행한다. 승인은 검토한 데이터와 평가 버전을 확인하고 기록한다.

승인 요청은 현재 신청 상태·데이터 버전·평가 버전·동의 유효성을 같은 DB 트랜잭션에서 검사한다. 평가 이후 자료 변경이나 동의 철회가 있었다면 오래된 화면에서의 승인을 충돌 오류로 거부한다.

경보와 상환 지원 요청은 별도 업무 상태로 표시한다. 내부 평가나 경보 전체를 사업자에게 자동 공개하지 않는다.

### 5.4 데모 제어

운영자만 합성 정산 지연, 일시적 원천 장애, 미납 사건, 시간 이동, 데이터 초기화를 실행한다. 업무 결과를 직접 성공으로 바꾸는 버튼은 만들지 않는다.

초기화는 확인을 받고 진행 중 작업을 중단한 후 앱 소유 데모 데이터만 대상으로 수행한다. Copilot 사용량·원격 기록이 초기화되었다고 표시하지 않는다.

UI 방향은 승인된 브라우저 시안의 사업자 중심 구성으로 한다. 시안의 비활성 버튼을 그대로 옮기는 것이 아니라 위 업무 동작을 구현한다.

## 6. 합성 데이터와 시간

### 6.1 기준 시점

초기 테스트 시각 D0는 `2026-10-28T00:00:00+09:00`이다. 6개월 은행 조회는 `2026-04-28T00:00:00+09:00` 이상, D0 미만의 반개구간으로 정의한다.

업무 날짜·동의 만료·상환 일정에는 주입된 테스트 시계를 사용한다. 네트워크 제한시간·재시도 대기·작업 임대시간에는 실제 시간을 사용해 시간 이동이 실행기 복구를 왜곡하지 않도록 한다.

### 6.2 원천 구성

은행 거래에는 자기 계좌 이체·영업 유입·대출금 등 검증 가능한 사례를 포함한다. 기초 잔액과 거래를 연결해 D0 잔액 300만 원과 일치시킨다. PG 자료는 정산 ID·기준 시점·예정일·순금액·상태를 포함한다. 세금 자료는 대상 신고기간과 출처를 갖는 합성 증빙이다.

기간 내 거래가 없다는 사실과 페이지 조회 실패를 구분한다. PG·세금 자료에 은행의 6개월 필터를 기계적으로 적용하지 않고 각 원천의 계약을 사용한다.

### 6.3 기본 유동성 사례

| 항목 | 시점 | 금액 |
|---|---|---|
| 현재 가용 잔액 | D0 | 300만 원 |
| 미지급 PG 순정산 | D+3 | +500만 원 |
| 급여 지출 예정 | D+5 | -600만 원 |
| 대출 상환 예정 | D+10 | -100만 원 |

확인된 일정만 계산하면 D+10 잔액은 100만 원이다. 정산 예정일을 D+8로 변경하면 D+5부터 정산 전까지 예상 잔액이 -300만 원이 된다. 이는 예상 부족이지 은행의 실제 마이너스 거래가 아니다.

심사 전 D+10의 100만 원은 신청한 대출 조건의 가정이며 실제 채무가 아니다. 승인 후 같은 일정을 모의 상환 일정으로 전환하고 전망에 중복 추가하지 않는다. 7일 전망의 정상 최저 잔액은 200만 원, 30일 전망의 정상 최저 잔액은 100만 원이다. 확인되지 않은 이후 현금흐름은 별도 불확실성으로 표시한다.

시간 이동만으로 예상 지출을 실제 계좌 출금으로 바꾸거나 미납을 추론하지 않는다. 실제 합성 지급·납부·미납 상태는 대응하는 사건으로 기록한다. 정산 입금 사건은 은행 입금과 PG 지급 상태를 같은 원천 DB 트랜잭션에서 일치시키고, 같은 사건 재실행은 중복 반영하지 않는다.

은행 입금과 정산 매출을 더하지 않는다. 현재 잔액에 아직 포함되지 않은 확인된 미지급 정산만 전망에 반영한다. 지급 여부가 불명확하면 기본 전망에서 제외하고 별도 확인 항목으로 표시한다.

7일·30일 잔액, 기간 내 최저 잔액·부족일을 코드로 계산한다. 금액은 원 단위 정수와 안전 범위 검사를 사용하고, 부동소수점 금액 연산을 피한다. 미래 매출을 임의로 예측하지 않는다.

## 7. 다섯 역할과 Copilot SDK

| 역할 | 코드·모델 경계 |
|---|---|
| Data Assembly | 코드가 동의 확인·HTTP 수집·완전성·중복 검증·정규화를 수행한다. |
| Underwriting | 모델이 확인된 요인·근거를 해석하고 필요한 조회·시나리오 도구를 선택해 심사 의견을 작성한다. |
| Early-Warning | 코드가 필수 위험 조건을 탐지하고 모델이 변화의 맥락과 추가 분석을 설명한다. |
| Collections | 모델이 고객 요청을 해석하고 승인된 지원 경로 중 하나를 제안한다. |
| Consent Lifecycle | 코드가 동의 범위·유효성·철회·갱신 기록·차단·삭제를 관리한다. |

### 7.1 실제 추론과 모델 선택

Node용 GitHub Copilot SDK를 서버에서만 사용한다. 앱이 관리하는 별도 SDK 런타임을 사용하며 현재 대화 세션을 재사용하거나 조작하지 않는다.

구현 시 SDK 인증 상태와 사용 가능한 모델 목록을 확인한다. 데모 운영자가 사용 가능한 모델 ID를 명시적으로 선택한 뒤 실제 추론을 활성화한다. 선택되지 않았거나 접근할 수 없으면 명확한 설정 오류를 표시하고 자동 모델 변경·모의 응답 대체를 하지 않는다.

같은 선택 모델을 세 역할에 사용하되 역할 지시·도구·세션은 분리한다. 모델 변경은 새 작업부터 적용하고 실행 기록에 모델 ID를 보관한다. 자동 테스트는 SDK 대역을 사용하지만 실제 데모 실행 경로와 분리한다.

### 7.2 도구와 세션 경계

사업자·작업·역할별 새 세션을 사용한다. 도구는 읽기 전용 자료·정책 조회 및 승인된 계산·시나리오 함수만 허용한다. 서버가 작업의 사업자·자료 버전을 도구에 결합하며, 모델이 다른 사업자 ID로 바꿀 수 없게 한다.

기본 파일·셸·웹·MCP·사용자 전역 도구 및 자동 확장을 허용하지 않는다. SDK 버전에 맞는 허용 목록과 권한 처리기를 적용하고 허용 목록 밖 도구를 거부한다. 광범위한 `approveAll`을 사용하지 않는다.

LLM에는 승인·발송·삭제·DB 수정 권한을 제공하지 않는다. 금융 원자료 전체 대신 필요한 합성 지표와 최소 근거를 전달한다. 고객의 자유 입력도 신뢰할 수 없는 자료로 취급한다.

모델 응답은 역할별 스키마로 검증한다. 평가의 `evidenceIds`는 해당 자료 묶음에서 확인되어야 한다. 화면의 금액은 모델이 생성한 수치가 아니라 코드 계산 값을 사용한다.

세션당 기본 제한은 120초, 도구 호출은 최대 8회다. 미완료·잘못된 출력·초과는 명시적인 실패로 기록하고 운영자가 재시도할 수 있게 한다. 실제 API 오류가 일시적인 경우에만 작업당 총 2회 이내로 자동 시도하고, 인증·정책 오류는 자동 재시도하지 않는다.

SDK의 일시 중단·종료와 별개로 늦게 도착한 결과는 작업·동의 버전을 다시 확인한 뒤 저장한다. 무효화된 작업의 결과는 폐기한다.

### 7.3 모델 실패 시 행동

Underwriting 실패 시 심사 완료로 표시하거나 승인을 허용하지 않는다. Early-Warning의 필수 규칙 경보는 모델 실패에도 유지하되 AI 설명 실패를 표시한다. Collections 실패 시 지원 요청은 담당자 검토 대기로 남기며 임의의 지원 결과로 대체하지 않는다.

## 8. 업무 상태와 실행

신청 상태, 수집 작업, 동의, 심사 평가, 대출·상환 상태를 하나의 상태 필드에 합치지 않는다.

신청은 `SUBMITTED → COLLECTING → ANALYZING → AWAITING_REVIEW → APPROVED / REJECTED`로 진행한다. 자료 문제는 `NEEDS_INFORMATION`, 작업 오류는 별도 작업의 `FAILED`, 동의 차단은 관련 작업의 `BLOCKED_BY_CONSENT`로 표현한다.

사업자가 신청을 제출하면 API는 작업 ID를 반환한다. 앱은 짧은 주기로 상태를 조회하며 완료·실패 후 해당 폴링을 종료한다. 백엔드 작업은 브라우저 수명과 무관하게 수행된다.

오케스트레이터는 SQLite 작업 테이블을 사용한다. 한 앱 프로세스의 실행기가 작업을 원자적으로 선점하고 임대·하트비트를 기록한다. 외부 HTTP·모델 호출 동안 DB 트랜잭션을 유지하지 않는다.

재시작 후 완료 작업은 재실행하지 않는다. 임대가 만료된 작업만 복구하며, 작업 키·결과 버전·고유 제약으로 중복 결과를 방지한다. 재시작 경계에서 모델 호출이 반복되어 사용량이 늘 수 있다는 한계를 기록한다.

원천 HTTP 조회는 제한시간 10초, 일시적 네트워크·5xx 오류에 총 3회 이내로 재시도한다. 동의·인증·잘못된 요청은 재시도하지 않는다.

전체 업무 순서는 코드가 결정한다. 모델 내부에서 어떤 추가 읽기·분석이 필요한지 선택하는 것은 허용하지만, 필수 선행조건은 생략하지 못한다.

## 9. 핵심 API와 데이터 계약

아래는 구현 시 유지할 논리적 계약이다.

| API | 책임 |
|---|---|
| `POST /api/demo-login` | 합성 테스트 계정 세션 발급 |
| `POST /api/consents` | 사업자의 명시적 동의 등록 |
| `POST /api/applications` | 동의를 확인하고 신청·수집 작업 생성 |
| `GET /api/applications/:id` | 권한에 따른 신청 요약 |
| `GET /api/jobs/:id` | 작업 상태·명시적 오류 조회 |
| `POST /api/applications/:id/review` | 담당자의 승인·거절·보완 결정 |
| `POST /api/support-requests` | 사업자의 지원·설명·정정·고충 요청 |
| `POST /api/consents/:id/revoke` | 동의 철회와 관련 작업 차단 |
| `POST /api/demo/events` | 운영자 합성 사건 생성 |
| `GET /api/ai/models` | 운영자 모델 설정을 위한 SDK 모델 목록 |
| `POST /internal/consents/authorize` | 인증된 mock 서버의 동의 검사 |
| `GET /v1/bank/transactions` | mock 은행 자료의 스냅샷·커서 기반 조회 |
| `GET /v1/pg/settlements` | mock PG 정산 스냅샷 조회 |
| `GET /v1/tax/documents` | mock 세금 자료 조회 |

부작용이 있는 요청은 멱등 키를 사용한다. 동일 키·동일 요청은 기존 결과를 반환하고, 동일 키·다른 요청은 충돌 오류로 처리한다.

모든 수집은 사업자·원천·목적·허용 자원·기간을 검증한다. 요청한 6개월이 동의된 3개월을 초과하면 명시적으로 거부하며 부분 성공처럼 표시하지 않는다.

데이터 묶음은 `dataset_id`, `version`, `as_of`, `source_snapshot_ids`, `validation_status`를 갖는다. 수집 시각·원천 발생 시각·시나리오 기준 시점을 구분한다. 거래의 원천 ID·계좌 ID에 고유 제약을 둔다.

페이지 응답은 고정 snapshot ID·총 건수·다음 커서를 제공한다. 커서 반복, 동일 ID의 상충 내용, 총 건수 불일치, 은행 기초·기말 잔액 불일치를 실패로 처리한다. 같은 원천 ID의 동일 내용은 한 번만 반영한다. 수집 도중 원천 snapshot이 변경되면 부분 결과를 공개하지 않고 새 스냅샷으로 작업을 다시 시작한다.

업무 SQLite에는 신청·동의·작업·정규화 자료·평가·결정·경보·상환·지원·안내·감사 메타데이터를 저장한다. 원천 SQLite에는 합성 기관 자료만 저장하고 에이전트가 직접 읽지 못하게 한다.

## 10. 만료·철회·삭제

동의는 심사 목적과 모니터링 목적을 분리한다. 기본 시연용 유효기간은 심사 D+30, 모니터링 D+60이며 화면에 명시한다. 기간 경과 후 자동 갱신하지 않는다.

철회·만료 시 해당 동의에 연결된 작업과 데이터 묶음을 먼저 무효화한다. 진행 중 조회는 중단하고, 이미 실행 중인 모델의 후속 도구 호출과 결과 저장도 차단한다.

차단은 요청 시 즉시 적용하며 주기적인 만료 처리기를 기다리지 않는다. 원천 서버도 매 페이지 생성 전과 응답 직전에 현재 동의를 확인한다. 앱의 최종 결과 저장은 동의 버전 검사를 포함한 트랜잭션으로 실행해 철회와 늦은 결과 저장 사이의 경쟁을 막는다.

동의별로 수집·파생 데이터의 계보를 관리한다. 다른 목적에 별도 근거가 있는 자료를 임의로 지우지 않도록 데이터 묶음을 동의별로 연결한다.

삭제 대상은 앱이 해당 동의로 확보한 거래·정산·세금 자료, 파생 AI 평가·설명, 캐시·원문 payload다. 삭제 후 그 내용을 화면에서 재열람할 수 없게 한다. 신청·사람의 결정 등 다른 근거의 업무 기록과 최소 작업 ID·시각·상태는 명시적인 별도 범위로 유지한다.

원천기관 역할의 mock DB는 삭제하지 않는다. 철회된 동의로는 다시 가져올 수 없어야 한다. 갱신은 새 명시적 동의로 기록하며 과거 삭제 자료를 자동 복원하지 않는다.

로컬 SDK 세션·출력도 앱 소유 기록과 연계해 정리하며, 정리 실패를 숨기지 않는다. 원격 Copilot 보존 정책까지 앱이 제어하거나 삭제했다고 주장하지 않는다. 첫 데모는 DB 백업·외부 분석 복제본을 만들지 않는다.

삭제 완료는 앱의 지정 범위에서 행·세션 기록·캐시가 제거되고 접근이 차단되었음을 뜻한다. 디스크 포렌식 수준의 안전 삭제를 보장한다는 뜻이 아니다. 운영 환경의 법정 보존·백업·국내 처리 적합성 검토는 별도 과제다.

## 11. 상환과 고객 보호

담당자 승인 전에는 모의 대출을 생성하지 않는다. 승인 시 해당 신청에 연결된 모의 상환 일정과 상태를 만든다.

정산 지연은 내부 경보를 유발하지만 미납이나 추심을 자동 생성하지 않는다. 별도 미납 사건·고객 지원 요청을 정책 입력으로 사용한다.

Collections는 `GENERAL_INQUIRY`, `PAYMENT_DIFFICULTY`, `DISPUTE_OR_CORRECTION`, `HUMAN_REVIEW` 같은 사전 정의 경로를 선택한다. 실제 고객 안내는 승인된 고정 템플릿과 검증된 변수로 구성하고 mock 발송함에만 기록한다.

동일 사건·템플릿의 중복 발송을 막고, 데모 기준일에 신청별 자동 안내는 최대 1건으로 제한한다. 채무 재조정은 제안·담당자 검토·명시적 승인 후 모의 반영하며 모델이 날짜·금액 변경을 약속하지 못한다.

## 12. 관측 가능성과 검증

작업 ID·신청 ID·역할·도구·입력 버전·상태·소요시간·모델 ID를 구조화해 기록한다. 원문 금융 payload·인증정보·모델 내부 사고과정을 일반 로그에 남기지 않는다.

SDK가 사용량 정보를 제공하면 그대로 기록하고, 제공되지 않으면 미확인으로 표시한다. 실제 청구액을 추정값이나 0원으로 가장하지 않는다.

| 검증 | 합격 기준 |
|---|---|
| 금액·날짜 | 기준 사례의 정상 D+10 100만 원, 지연 D+5 -300만 원과 일치. 6개월 경계 정확 |
| 자료 완전성 | 페이지 누락·중복·스냅샷 오류를 탐지하고 불완전 자료로 평가를 완료하지 않음 |
| 동의 | 미동의·기간 초과·철회·만료 이후 수집 및 후속 이용 차단 |
| 격리 | 다른 사업자·역할의 자료 조회·승인·사건 생성 거부 |
| 복구 | 재시작 후 미완료 작업을 복구하고 승인·안내·입금 사건을 중복 반영하지 않음 |
| 모델 경계 | 승인·셸·파일 도구 접근 차단, 근거 ID 검증, 오류·제한 초과 표시 |
| 삭제 | 앱 수집 자료·파생 결과 접근 불가, 지정 데이터 제거, 원천은 보존하되 재조회 차단 |
| 전체 여정 | 신청·동의·실제 HTTP 수집·실제 SDK 평가·사람 승인·경보·지원·삭제 확인 |

자동 테스트는 계산·상태·API·권한·복구에 집중하고 모델 대역을 사용한다. 실제 SDK smoke test는 별도 명령으로 합성 입력만 보내며, 모델·인증 문제가 있으면 불완료로 보고한다.

브라우저 시나리오는 정상 신청, 보완·장애 복구, 승인, 정산 지연, 지원 요청, 만료·삭제를 다룬다. 테스트 대역 통과만으로 실제 SDK 연동이 완료되었다고 판단하지 않는다.

## 13. 산출물과 완료 조건

- 실행 가능한 로컬 웹앱과 별도 mock API.
- 원문의 5개 역할 모듈과 실제 Copilot SDK 연동.
- 합성 seed, 사건 제어, 앱 데이터 초기화.
- 자동 테스트와 별도 실제 SDK·브라우저 확인 절차.
- README: 실행·종료·모델 선택·비용·실패 복구·데이터 위치·한계.
- 타임라인: 누가 어떤 근거로 무엇을 실행했고 어느 단계에서 실패했는지 확인.

아직 구현하지 않은 금융기관 연결·운영 인증·법적 적합성·국내 추론·Fabric·Durable Functions를 완료로 표시하지 않는다. 원문의 비용 60% 절감·48시간 심사·60~90일 선행 경보·신용비용 감소는 이 데모의 검증 성과가 아니다.
